## Project overview

NOVIRA is a two-part app that helps people from the Middle East/North Africa region find the best pathway (university, Ausbildung, or employment) to Germany. Users complete a 14-step assessment (country, age, education, occupation field, work experience, desired path, language levels + certification, passport status, prior Germany connection, financial situation, timeline, region flexibility) modeled on real German labor-market demand and Egypt-specific factors, not just generic profile fields. The Tier 1 verdict is computed entirely client-side by a rules engine (`frontend/src/lib/assessment-verdict.ts`, see "Matching algorithm" below) — the backend is not involved in this step at all.

- `frontend/` — Next.js 16 (App Router) + React 19 + TypeScript + Tailwind v4 + DaisyUI. Owns the entire UI, including the assessment wizard, and currently persists assessment answers to `localStorage` only.
- `backend/` — ASP.NET Core (.NET 9) minimal API with EF Core + Npgsql wired to a Postgres database (Azure Database for PostgreSQL — Flexible Server, migrated from Neon 2026-08-15; see the "Database hosting" note under Backend conventions for why and what's still open). `Models/` (`User.cs`, `Opportunity.cs`, `MagicLinkToken.cs`, `Session.cs`, `UserDocument.cs`, `Message.cs`, `Purchase.cs`, `IntakeProfile.cs`, `CvRequest.cs`, `CvDraftContent.cs`, `CvReferenceSettings.cs`), `Data/` (`AppDbContext.cs`), `Services/` (`MatchingService.cs`, `TokenGenerator.cs`, `OpportunitySyncService.cs`, `OccupationFieldMapper.cs`, `BundesagenturJobsucheClient.cs`, `AzureBlobStorageService.cs`, `DocumentVerificationService.cs`, `ResendEmailService.cs`, `EffectiveTierCalculator.cs`, `TierPricing.cs`, `StripeCheckoutClient.cs`, `LiveMessagingTicketStore.cs`, `GermanStateMapper.cs`, `CvGenerationService.cs`, `CvPdfRenderer.cs`), `Endpoints/` (`OpportunitiesAdminEndpoints.cs`, `MatchingEndpoints.cs`, `OpportunityCountsEndpoints.cs`, `AuthEndpoints.cs`, `AdminAuthFilter.cs`, `SessionAuthFilter.cs`, `DocumentsEndpoints.cs`, `DocumentsAdminEndpoints.cs`, `AccountEndpoints.cs`, `MessagesEndpoints.cs`, `PurchasesEndpoints.cs`, `IntakeEndpoints.cs`, `CvRequestsEndpoints.cs`, `CvRequestsAdminEndpoints.cs`, `CvReferenceSettingsAdminEndpoints.cs`), `Hubs/` (`MessagesHub.cs`, SignalR) — `Program.cs` stays the thin composition root plus the inline `POST /leads` handler. ## Working methodology

**Breadth-first, not depth-first (as of 2026-07-31):** get each new piece of the user journey minimally working end-to-end before polishing any single piece, rather than fully finishing/polishing one component before starting the next. This is a deliberate choice for a prototype whose purpose is to be demoed and get feedback — polishing early risks investing in details that get reworked once the full flow is validated. Don't proactively suggest polishing an already-working piece; keep moving across the skeleton unless told otherwise.

The condition that makes this safe: every shortcut, blocker skipped, or known weakness accepted to keep moving **must be tracked, not silently dropped** — add it to "Deferred" in Current build phase below, or to a "Known limitations" note near the relevant architecture section (see the "Known security limitations" pattern under Email capture & result email), the same way the old `PlaceholderOpportunityCounts.tsx` was loudly marked as mock rather than quietly left ambiguous until it was replaced with real data (`OpportunityCounts.tsx`, 2026-08-10). Once the full skeleton exists, come back and harden/polish step by step — that pass is expected to follow, not skipped forever.

## Pre-deployment blockers

Tracked here as a single checklist specifically so none of these get lost across scattered sections — **do not deploy this app publicly until all of these are addressed.** Each links to where the full reasoning/context lives. Distinct from the phase checklists above: these aren't unfinished features, they're known-safe-for-local-dev-only gaps that become real problems the moment this is reachable from the public internet.

- [ ] **Rate limiting is bypassable via `X-Forwarded-For` spoofing (found 2026-08-12).** Every frontend Route Handler's rate limit — `/leads`, `/opportunity-counts`, `/auth/request-link` — partitions by `request.headers.get('x-forwarded-for')` (each route's own `getClientIp()`, see `src/lib/rate-limit.ts` for the shared limiter itself), which is attacker-controlled unless a real reverse proxy strips/overwrites it before the app ever sees it. Not exploitable today — the app only runs on `localhost`, nothing sits in front of it — but once deployed this fully defeats per-visitor throttling on all three routes. Most consequential on `/auth/request-link` specifically: a bypassed limit there means unlimited magic-link email-bombing to any victim's inbox, not just free-service abuse. Deliberately not fixed yet — the right fix depends on the actual hosting target (e.g. Vercel's own trustworthy forwarded-for header vs. a custom reverse-proxy's trusted-hop config), and guessing at that now risks either doing nothing useful or creating false confidence in a rate limit that still doesn't work.
- [ ] **`ASPNETCORE_ENVIRONMENT=Development`** in `launchSettings.json` — must become `Production`. Development mode's diagnostics can be more verbose on unhandled errors, and (new as of the auth system, see "Account signup" below) the `/auth/request-link` dev-only magic-link log line only stops firing once this is genuinely `Production`.
- [ ] **CORS is locked to `http://localhost:3000`** (`Program.cs`) — update the policy alongside whatever the real frontend origin becomes.
- [ ] **Resend's sending domain isn't verified — the single most urgent item on this whole list, not just one entry among equals.** Without it, `onboarding@resend.dev` (the shared sandbox address every email currently sends from) can only deliver to the email address that owns the Resend account itself — i.e., only to the founder. Affects both the result email and, critically, the magic-link sign-in email: a real stranger who signs up with their own email has their magic link silently fail to arrive — no error, no crash, just an email neither side ever sees. Every other piece of the app (payments, matching, document upload) can work perfectly while this one gap quietly makes it impossible for anyone but the founder to ever sign in — and it has stayed invisible so far for exactly that reason, since every test to date has used the founder's own email. See `Plan.md` §14 ("Path to first real revenue") for why this is first on that list too, not just this one.
- [ ] **No security response headers anywhere** — no CSP, `X-Frame-Options`, HSTS, etc., configured on either the backend or `next.config`. Not yet designed, just genuinely absent.
- [ ] **Database is hosted in West US, not the EU** — the Azure free-trial subscription used to create `novira-postgres` currently rejects provisioning in every EU region tried (Germany West Central: capacity-blocked for non-EA customers; West Europe: also rejected) — a real, documented Azure capacity/policy restriction on trial subscriptions, not something fixable via a portal setting. Fine for now (dev-only, synthetic/founder's-own data, same reasoning as the document-upload pipeline's own deferral), but real user data (self-reported profiles, and especially uploaded documents once that's opened beyond testing) must live in an EU/EEA region before this is public, given the userbase and GDPR. Fix path: upgrade off the free trial to Pay-As-You-Go (unlocks EU regions) or request region access via an Azure support ticket, then re-run the same Neon→Azure-style migration once more, this time Azure region → Azure region.
- [ ] **`documents-upload`'s backend rate limit partitions by IP, not by session (found 2026-08-28 code review).** Same underlying shape as the `X-Forwarded-For` issue above but a distinct root cause — this one isn't fixed by trusting/not-trusting a header. Since all browser traffic goes through the single Next.js proxy, `RemoteIpAddress` collapses to one value for every signed-in user, so the 10/min policy is effectively one shared global bucket rather than a per-user cap. One user bursting uploads would 429 every other user's real, paid Claude-vision call. Needs a per-session/per-user partition key instead of IP.

## Known issues from code review (found 2026-08-28)

A full multi-angle code review ran over everything built this session (auth, document pipeline, messaging, admin reorg — all the dated entries in "Document verification pipeline" below) before any of it had been formally reviewed, only live-tested. Each finding was independently verified against the actual code, not just diff text. Being worked through one at a time on the `fix/code-review-findings` branch — check items off as they're fixed rather than deleting the list, so the review's coverage stays visible.

**Real bugs / security gaps:**
- [x] **`POST /auth/request-link` overwrites a user's profile before proving they own that email — fixed 2026-08-28.** Was: `RequestLinkRequest.Profile`, when present, was written onto the `Users` row immediately, before the magic link was ever clicked — anyone who knew a victim's email could silently corrupt their stored profile (which then feeds real `/matches` results), without ever proving inbox ownership. Worse than the already-accepted "no auth on `/leads`" tradeoff (see "Known security limitations" below), because it mutated data used for real results, not just a one-time capture. **Fix**: `MagicLinkToken` gained `PendingProfileJson` — `/auth/request-link` now stashes the (JSON-serialized) profile on the token instead of writing it to `user`; `/auth/verify` applies it to `user` only after the atomic single-use claim succeeds, i.e. only once ownership of the inbox is actually proven. Migration `AddPendingProfileToMagicLinkToken`. **Verified live against the real attack scenario, not just compiled**: created a victim user with a real profile (`Egypt`/`nursing`) → POSTed to `/auth/request-link` with the victim's email and a bogus profile (`ATTACKER-CORRUPTED`/`hacked`), never clicking any link → confirmed via `GET /admin/users/{id}` that the victim's real profile was **untouched** immediately after. Then verified the legitimate path still works: consumed the dev-logged token (simulating the real owner clicking it) → confirmed the pending profile *did* then apply, proving the mechanism is correct, not just inert — the vulnerability required actual inbox access to complete, which is the correct trust boundary. Test user deleted afterward.
- [x] **A fraud-flagged user's upload error was silently dropped — fixed 2026-08-28.** Was: `POST /documents`'s fraud-block returned `Results.Problem()` (a `detail` field); `frontend/src/lib/api/documents.ts` only reads `body.message`, so instead of seeing why uploads are blocked, the user just got a generic "Failed to upload document." **Fix**: fraud-block now returns `Results.Json(new { message = ... }, statusCode: 403)`, matching the `{ message }` shape every other error in this file (and the frontend's error handling) already expects. **Verified live, not just compiled**: created a test user, uploaded a throwaway document, `FlaggedRed`'d it via the real admin endpoint (confirmed `user.FraudFlagged` was set), then attempted a second upload as that same user — the real HTTP response was `403` with body `{"message":"Uploads are currently unavailable for this account. Contact support if you believe this is a mistake."}`, the exact explanatory text now reaching the frontend instead of a dropped `detail` field. Test user deleted afterward.
- [x] **Stale admin copy — fixed 2026-08-28**: the document-review note textarea said the note is "included in the email for Deny / Flag red" — untrue since messaging moved in-app (2026-08-27, see below). **Fix**: placeholder now reads "shown to the user in their in-app message for Deny / Flag red."
- [x] **Approving a document promoted `Verified*` data with no unwind if the document was later reclassified — fixed 2026-08-28.** Was: `ApplyVerifiedDataFromDocument` only ever wrote fields on Approve; a document later discovered fraudulent and reclassified to `FlaggedRed`/`Denied` left its promoted data (identity, education, language level) sitting on the account indefinitely, still feeding real `/matches` results, with no way to retract it — not even the existing `recompute-verified-data` catch-up endpoint helped, since it also only ever added/overwrote, never cleared. **Fix**: replaced the incremental "apply on Approve" model with a full re-derivation, `DocumentsAdminEndpoints.cs`'s new `RecomputeVerifiedData` — wipes all 11 `Verified*` fields, then re-applies `ApplyVerifiedDataFromDocument` over whatever is *currently* Approved (oldest upload first, same "last write wins" ordering it already had). Simpler and more robust than tracking which document contributed which field for a targeted unwind. Now runs on every review decision in the `PATCH /admin/users/{userId}/documents/{documentId}` handler (not just Approve), and the standalone recompute endpoint reuses the identical helper. **Verified live end-to-end, not just compiled** (seeded two fake-but-already-AI-verified documents directly into the real DB for a throwaway test user, skipping a real paid Claude vision call since this fix is entirely downstream of extraction — same reasoning as the `DateOnly` fix's verification): Approved a fake Passport → confirmed identity fields (`verifiedFullName`/`verifiedNationality`/`verifiedPassportNumber`/etc.) populated. Approved a fake EducationCertificate too → confirmed both documents' fields coexisted, neither clobbering the other. Reclassified the passport to `FlaggedRed` → confirmed its fields (`verifiedFullName` included, since only the passport had supplied it) cleanly unwound to `null` while the still-Approved certificate's fields (`verifiedHighestEducation`/`verifiedFieldOfStudy`) survived untouched — the actual scenario this bug was about. Denied the certificate too → confirmed all 11 `Verified*` fields (including `verifiedDataUpdatedAt` itself) went back to `null`. Also smoke-tested the standalone `/recompute-verified-data` endpoint post-refactor. Test user and seeded documents deleted afterward via the real `DELETE /admin/users/{id}`.
- [x] **Passport-expiry parsing (`DateOnly.TryParse`) used ambient server culture, not an explicit invariant format — fixed 2026-08-28.** Was: a valid AI-extracted ISO date (`yyyy-MM-dd`) could silently fail to parse (or misparse) depending on the server's ambient culture/calendar, quietly dropping `VerifiedPassportStatus` with no error surfaced anywhere. **Fix**: `DateOnly.TryParseExact(extracted.ExpiryDate, "yyyy-MM-dd", CultureInfo.InvariantCulture, DateTimeStyles.None, out var expiry)`. **Verified the actual failure mode, not just the fix** (without spending a real paid Claude vision call to exercise this one line): a throwaway console script confirmed that under `ar-SA` culture — which defaults to the Umm al-Qura (Hijri) calendar in .NET — the old plain `DateOnly.TryParse("2027-03-15", ...)` genuinely returned `success=False`, a real reproduction of the bug, not a hypothetical; the new `TryParseExact` with `InvariantCulture` correctly parsed it to `2027-03-15` regardless. Scratch project deleted afterward.
