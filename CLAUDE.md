# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

NOVIRA is a two-part app that helps people from the Middle East/North Africa region find the best pathway (university, Ausbildung, or employment) to Germany. Users complete a 14-step assessment (country, age, education, occupation field, work experience, desired path, language levels + certification, passport status, prior Germany connection, financial situation, timeline, region flexibility) modeled on real German labor-market demand and Egypt-specific factors, not just generic profile fields. The Tier 1 verdict is computed entirely client-side by a rules engine (`frontend/src/lib/assessment-verdict.ts`, see "Matching algorithm" below) — the backend is not involved in this step at all.

- `frontend/` — Next.js 16 (App Router) + React 19 + TypeScript + Tailwind v4 + DaisyUI. Owns the entire UI, including the assessment wizard, and currently persists assessment answers to `localStorage` only.
- `backend/` — ASP.NET Core (.NET 9) minimal API with EF Core + Npgsql wired to a Postgres database (Azure Database for PostgreSQL — Flexible Server, migrated from Neon 2026-08-15; see the "Database hosting" note under Backend conventions for why and what's still open). `Models/` (`User.cs`, `Opportunity.cs`, `MagicLinkToken.cs`, `Session.cs`, `UserDocument.cs`, `Message.cs`), `Data/` (`AppDbContext.cs`), `Services/` (`MatchingService.cs`, `TokenGenerator.cs`, `OpportunitySyncService.cs`, `OccupationFieldMapper.cs`, `BundesagenturJobsucheClient.cs`, `AzureBlobStorageService.cs`, `DocumentVerificationService.cs`, `ResendEmailService.cs`), `Endpoints/` (`OpportunitiesAdminEndpoints.cs`, `MatchingEndpoints.cs`, `OpportunityCountsEndpoints.cs`, `AuthEndpoints.cs`, `AdminAuthFilter.cs`, `SessionAuthFilter.cs`, `DocumentsEndpoints.cs`, `DocumentsAdminEndpoints.cs`, `AccountEndpoints.cs`, `MessagesEndpoints.cs`) — `Program.cs` stays the thin composition root plus the inline `POST /leads` handler. Real endpoints: `GET /` (health check), `POST /leads` (email capture + result email), `GET/PATCH /admin/opportunities` + `POST /admin/opportunities/sync-ausbildung` + `POST /admin/match-preview` (admin-key protected), `POST /opportunity-counts` (public, rate-limited, counts only), `POST /auth/request-link` + `POST /auth/verify` + `GET /auth/me` + `POST /auth/logout` (magic-link auth), `GET /matches` (session-authenticated, full match details — see "Account signup" below), `GET/POST /documents` (session-authenticated, document upload — see "Document verification pipeline" below), `GET /messages` + `POST /messages/read-all` (session-authenticated, in-app messages — see the in-app messaging entry below), `GET/DELETE /account` (session-authenticated self-service), and `GET /admin/users` + `GET /admin/users/{id}` + `PATCH /admin/users/{userId}/documents/{documentId}` + `POST /admin/users/{userId}/message` + `DELETE /admin/users/{id}` + `POST /admin/users/{id}/recompute-verified-data` (admin-key protected, the human-review side of the same pipeline). `frontend/.env.example` documents `API_BASE_URL=http://localhost:5080`, read server-side only by Next.js Route Handlers (`src/app/api/leads/`, `src/app/api/admin/opportunities/`, `src/app/api/auth/`, `src/app/api/matches/`, `src/app/api/documents/`, `src/app/api/messages/`, `src/app/api/account/`, `src/app/api/admin/users/`) — the browser never talks to the backend directly; `src/lib/api/` and `src/lib/contracts/` hold the client-side fetch wrappers and shared request/response types for this.

The two apps are run and deployed independently — there is no shared package/workspace tooling tying them together.

**Full business/legal/product reasoning** (legal scope constraints, the two-tier user funnel, why the Tier 1 verdict is a rules engine and not an LLM call, why the UI is English-first for now) lives in `Plan.md`, not here — read it before adding features that touch matching logic, user data collection, or anything advice/eligibility-adjacent. **The matching algorithm's own research and design** (real German university/Ausbildung/employment criteria, the draft scoring weights, open tuning questions) lives in `Matching-Algorithm-Study.md` — read it before changing anything in `lib/assessment-verdict.ts` or `lib/occupation-demand.ts`. This file only tracks the short technical version: what phase we're building right now.

## Working methodology

**Breadth-first, not depth-first (as of 2026-07-31):** get each new piece of the user journey minimally working end-to-end before polishing any single piece, rather than fully finishing/polishing one component before starting the next. This is a deliberate choice for a prototype whose purpose is to be demoed and get feedback — polishing early risks investing in details that get reworked once the full flow is validated. Don't proactively suggest polishing an already-working piece; keep moving across the skeleton unless told otherwise.

The condition that makes this safe: every shortcut, blocker skipped, or known weakness accepted to keep moving **must be tracked, not silently dropped** — add it to "Deferred" in Current build phase below, or to a "Known limitations" note near the relevant architecture section (see the "Known security limitations" pattern under Email capture & result email), the same way the old `PlaceholderOpportunityCounts.tsx` was loudly marked as mock rather than quietly left ambiguous until it was replaced with real data (`OpportunityCounts.tsx`, 2026-08-10). Once the full skeleton exists, come back and harden/polish step by step — that pass is expected to follow, not skipped forever.

## Pre-deployment blockers

Tracked here as a single checklist specifically so none of these get lost across scattered sections — **do not deploy this app publicly until all of these are addressed.** Each links to where the full reasoning/context lives. Distinct from the phase checklists above: these aren't unfinished features, they're known-safe-for-local-dev-only gaps that become real problems the moment this is reachable from the public internet.

- [ ] **Rate limiting is bypassable via `X-Forwarded-For` spoofing (found 2026-08-12).** Every frontend Route Handler's rate limit — `/leads`, `/opportunity-counts`, `/auth/request-link` — partitions by `request.headers.get('x-forwarded-for')` (each route's own `getClientIp()`, see `src/lib/rate-limit.ts` for the shared limiter itself), which is attacker-controlled unless a real reverse proxy strips/overwrites it before the app ever sees it. Not exploitable today — the app only runs on `localhost`, nothing sits in front of it — but once deployed this fully defeats per-visitor throttling on all three routes. Most consequential on `/auth/request-link` specifically: a bypassed limit there means unlimited magic-link email-bombing to any victim's inbox, not just free-service abuse. Deliberately not fixed yet — the right fix depends on the actual hosting target (e.g. Vercel's own trustworthy forwarded-for header vs. a custom reverse-proxy's trusted-hop config), and guessing at that now risks either doing nothing useful or creating false confidence in a rate limit that still doesn't work.
- [ ] **`ASPNETCORE_ENVIRONMENT=Development`** in `launchSettings.json` — must become `Production`. Development mode's diagnostics can be more verbose on unhandled errors, and (new as of the auth system, see "Account signup" below) the `/auth/request-link` dev-only magic-link log line only stops firing once this is genuinely `Production`.
- [ ] **CORS is locked to `http://localhost:3000`** (`Program.cs`) — update the policy alongside whatever the real frontend origin becomes.
- [ ] **Resend's sending domain isn't verified** — without it, `onboarding@resend.dev` can only deliver to the email on the Resend account itself (fine for dev, not for real users). Affects both the result email and the magic-link sign-in email.
- [ ] **No security response headers anywhere** — no CSP, `X-Frame-Options`, HSTS, etc., configured on either the backend or `next.config`. Not yet designed, just genuinely absent.
- [ ] **Database is hosted in West US, not the EU** — the Azure free-trial subscription used to create `novira-postgres` currently rejects provisioning in every EU region tried (Germany West Central: capacity-blocked for non-EA customers; West Europe: also rejected) — a real, documented Azure capacity/policy restriction on trial subscriptions, not something fixable via a portal setting. Fine for now (dev-only, synthetic/founder's-own data, same reasoning as the document-upload pipeline's own deferral), but real user data (self-reported profiles, and especially uploaded documents once that's opened beyond testing) must live in an EU/EEA region before this is public, given the userbase and GDPR. Fix path: upgrade off the free trial to Pay-As-You-Go (unlocks EU regions) or request region access via an Azure support ticket, then re-run the same Neon→Azure-style migration once more, this time Azure region → Azure region.
- [ ] **`documents-upload`'s backend rate limit partitions by IP, not by session (found 2026-08-28 code review).** Same underlying shape as the `X-Forwarded-For` issue above but a distinct root cause — this one isn't fixed by trusting/not-trusting a header. ## Known issues from code review (found 2026-08-28)

A full multi-angle code review ran over everything built this session (auth, document pipeline, messaging, admin reorg — all the dated entries in "Document verification pipeline" below) before any of it had been formally reviewed, only live-tested. Each finding was independently verified against the actual code, not just diff text. Being worked through one at a time on the `fix/code-review-findings` branch — check items off as they're fixed rather than deleting the list, so the review's coverage stays visible.

**Real bugs / security gaps:**
- [x] **`POST /auth/request-link` overwrites a user's profile before proving they own that email — fixed 2026-08-28.** Was: `RequestLinkRequest.Profile`, when present, was written onto the `Users` row immediately, before the magic link was ever clicked — anyone who knew a victim's email could silently corrupt their stored profile (which then feeds real `/matches` results), without ever proving inbox ownership. Worse than the already-accepted "no auth on `/leads`" tradeoff (see "Known security limitations" below), because it mutated data used for real results, not just a one-time capture. **Fix**: `MagicLinkToken` gained `PendingProfileJson` — `/auth/request-link` now stashes the (JSON-serialized) profile on the token instead of writing it to `user`; `/auth/verify` applies it to `user` only after the atomic single-use claim succeeds, i.e. only once ownership of the inbox is actually proven. Migration `AddPendingProfileToMagicLinkToken`. **Verified live against the real attack scenario, not just compiled**: created a victim user with a real profile (`Egypt`/`nursing`) → POSTed to `/auth/request-link` with the victim's email and a bogus profile (`ATTACKER-CORRUPTED`/`hacked`), never clicking any link → confirmed via `GET /admin/users/{id}` that the victim's real profile was **untouched** immediately after. Test user deleted afterward.
- [ ] **A fraud-flagged user's upload error is silently dropped.** `POST /documents`'s fraud-block returns `Results.Problem()` (a `detail` field); `frontend/src/lib/api/documents.ts` only reads `body.message`, so instead of seeing why uploads are blocked, the user just gets a generic "Failed to upload document."
- [ ] **Stale admin copy**: the document-review note textarea still says the note is "included in the email for Deny / Flag red" — untrue since messaging moved in-app (2026-08-27, see below). An admin could reasonably under-communicate, assuming email carried the note when only `/account` does.
- [ ] **Approving a document promotes `Verified*` data with no unwind if the document is later reclassified** (e.g. Approved, then discovered fraudulent and FlaggedRed). The account keeps using the promoted data for matching with no path to retract it.
- [ ] **Passport-expiry parsing (`DateOnly.TryParse`) uses ambient server culture, not an explicit invariant format** — could silently fail to parse a valid AI-extracted ISO date on a non-US-locale server, quietly dropping `VerifiedPassportStatus` with no error surfaced anywhere.

## Architecture

### Assessment wizard (the core frontend feature)
The wizard's data model, state, validation, and rendering are split across four layers — when changing a question, all of them may need updates:

1. **Schema** — `src/types/assessment.ts` defines the canonical question/step schema (`ASSESSMENT_QUESTION_DEFINITIONS`, `ASSESSMENT_STEP_DEFINITIONS`), enums (e.g. `EducationLevel`, `DesiredPath`, `LanguageLevel`), and the `AssessmentState`/`AssessmentAnswers` shape.
2. **State** — `src/context/AssessmentProvider.tsx` is a reducer-based React context (hydrate/update-answer/go-to-step/reset) providing the current step, answers, and navigation actions. Consumed via the `useAssessment()` hook (`src/hooks/useAssessment.ts`); must be used inside `<AssessmentProvider>` (wired in `src/app/assessment/page.tsx`, its own route — not embedded on the homepage, to keep the marketing page from competing with a 14-step form for attention).
3. **Persistence** — `src/lib/assessment-storage.ts` saves/loads a versioned envelope (`ASSESSMENT_STORAGE_VERSION`) to `localStorage` under `ASSESSMENT_STORAGE_KEY`, with normalization for legacy shapes (e.g. migrating an old `education` field to `highestEducation`). Bump the version and extend `normalizeAssessmentState` when the answer shape changes.
4. **Validation** — `src/lib/assessment-validation.ts` validates per-question (`validateQuestionAnswer`, dispatched by `question.kind`) and per-step (`validateStep`), driven off the same `ASSESSMENT_QUESTION_DEFINITIONS`.

`AssessmentWizard.tsx` derives its per-question render config (`WIZARD_QUESTIONS`) directly from `ASSESSMENT_STEP_DEFINITIONS`/`ASSESSMENT_QUESTION_DEFINITIONS` at module scope — there is no second copy of question text/options to keep in sync. Adding or editing a question only requires changing `types/assessment.ts` (each question needs a `prompt`, the full question text shown to the user, in addition to its short `label`).

Two question-rendering variants beyond the plain option-card grid, both driven by flags on the question definition (`AssessmentStep.tsx` branches on them):
- **`searchable: true`** — renders `SearchableSelect.tsx` instead of a card grid: an always-visible, in-flow filterable list (not a floating overlay — that caused a stacking-context bug with the nav buttons, see git history) with category group-headers shown once per group, not repeated per row. Used for `occupationField` (110 options across 17 categories).
- **`multiSelect: true`** — `AssessmentStep.tsx` toggles values in/out of an array instead of overwriting, uses `role="group"` instead of `radiogroup`. The answer type for that field must be an array (e.g. `germanyConnection: GermanyConnection[]`), and `AssessmentWizard.tsx`'s `answeredCount` must treat an empty array as unanswered, not answered — both already handled, but a trap if a new multi-select field is added without checking.

`StepIndicator.tsx` is a horizontally-scrolling carousel (not a wrapping grid) that re-centers on the active step via `scrollIntoView` whenever `currentStepIndex` changes — it does not have its own prev/next controls, it only follows the wizard's own navigation.

The assessment lives at its own route, `frontend/src/app/assessment/page.tsx` — not embedded on the homepage — specifically so a 14-question form doesn't compete with marketing/trust content for attention.

### Matching algorithm
- `frontend/src/lib/assessment-verdict.ts` — `computeVerdict(answers)` is the Tier 1 rules engine. It scores the profile against all three paths (University/Ausbildung/Employment) independently, then compares against the user's stated `desiredPath` to produce one of four outcomes (`confirmed` / `alternative` / `suggested` / `unclear`) — see `Matching-Algorithm-Study.md` §5.1 for why it's structured this way rather than a single flat verdict. Each `PathScore` also carries a `factors: ScoreFactor[]` breakdown (per-question point contributions), which `getImprovementAdvice()` uses to find the single weakest *actionable* factor for a path and return real, non-fabricated advice text (or `null` when nothing meaningful stands out). All scoring is internal; only the qualitative outcome and advice text may ever reach the UI.
- `frontend/src/lib/occupation-demand.ts` — a static, manually-curated lookup tagging which of the 110 `OccupationField` values are official German shortage occupations. Deliberately kept separate from `types/assessment.ts` (not part of the questionnaire schema, never shown to the user) so it's a clean swap-out point for the planned Phase 2 system: an AI-assisted pipeline that checks official sources periodically and regenerates this data.
- `frontend/src/lib/origin-country-requirements.ts` (built 2026-08-12) — same separation principle, applied to origin-country-specific document procedure (e.g. Egypt's Ministry of Foreign Affairs certificate pre-authentication) instead of occupation demand. Kept out of `result-display.ts`'s per-path checklists, which describe German-side demand only and are the same regardless of which country a user comes from — see `Matching-Algorithm-Study.md` §8 for why the two must stay separate as more MENA countries are added. `getDocumentChecklistItems(highlightedPath, country)` merges the two at read time. Only Egypt is populated so far.
- Wired into the UI at `frontend/src/app/assessment/result/page.tsx`, which loads the saved answers from `localStorage`, calls `computeVerdict()`, and renders, in order: the verdict text, `PathFitChart.tsx` (an "emphasis" bar chart — recommended path in the brand accent, the other two gray, no numeric labels anywhere per the qualitative-only rule), `EligibilityChecklist.tsx`, `ProfileImprovementAdvice.tsx` (real data from `getImprovementAdvice()`), `DocumentChecklist.tsx` (general, path-specific, publicly-sourced document info — not personalized advice, see the disclaimer in the component), `SaveResultPrompt.tsx`, and `OpportunityCounts.tsx`.
- **`OpportunityCounts.tsx` is real data**, not the mock `PlaceholderOpportunityCounts.tsx` it replaced (deleted 2026-08-10) — see the "Real opportunity count" bullet under Phase 1 above for how it's wired end to end (`POST /opportunity-counts` → `MatchingService`).

### Email capture & result email
- `SaveResultPrompt.tsx` (rendered on `/assessment/result`, after the document checklist) posts to `src/lib/api/leads.ts` → `src/app/api/leads/route.ts` (server-side proxy, keeps `API_BASE_URL` off the client) → backend `POST /leads`.
- The backend does **not** recompute anything — it trusts the frontend's already-computed, already-qualitative display data (verdict heading/body, `getImprovementAdvice()` output, the fixed-band path-fit bars from `src/lib/result-display.ts`, the static per-path document checklist) and just relays it into a branded HTML email (`BuildResultEmailHtml` in `backend/Program.cs`). This keeps the "no scoring server-side" rule from the Matching algorithm section intact — see the security note below for the trade-off this creates.
- `src/lib/result-display.ts` is the single source of truth for path-fit labels/bar widths and the per-path document checklists — both `PathFitChart.tsx`/`DocumentChecklist.tsx` (on-page) and `result/page.tsx`'s email payload read from it, so there's no second copy to drift.
- The email template is table-based with inline styles throughout (not Tailwind classes, not flexbox/grid) because desktop Outlook renders with Word's engine and ignores both — see the comment above `BuildResultEmailHtml`.
- Email sending uses [Resend](https://resend.com) (`Resend:ApiKey` / `Resend:FromAddress` in backend user-secrets, never committed). Without a verified sending domain on Resend, `onboarding@resend.dev` can only deliver to the email on the Resend account itself — fine for dev, not for real users. Domain verification is a prerequisite before this reaches anyone outside the founder.
- If `Resend:ApiKey` is unset (or the Resend call fails), `POST /leads` still saves the `Users` row and returns `{ saved: true, emailSent: false }` — a flaky/unconfigured email provider must never mask a successful capture.

#### Known security limitations (tracked, not all fixed)
As of 2026-07-30, `/leads` has: per-IP rate limiting at **both** layers (Next.js route handler, `src/lib/rate-limit.ts`, keyed off `X-Forwarded-For` — see "Pre-deployment blockers" above for why that header can't actually be trusted yet; and backend, `Program.cs`'s `AddRateLimiter` — coarser, since it only ever sees the frontend proxy's IP for browser traffic), email normalization before the uniqueness check, request field/array-size caps (`IsWithinSizeLimits`), the branded CTA button restricted to the configured frontend origin only (`IsAllowedContinueUrl`, prevents it being turned into an open phishing-link redirector), an HTTP timeout on the outbound Resend call, and a catch-all around the handler so internal exceptions never reach the client. Still open, deliberately deferred:
- **No auth on `/leads`, by design** (Tier 1 is explicitly no-signup) — this means rate limiting + input caps are the *only* real defense, not identity. Acceptable while this stays local/prototype-only; revisit before any public deployment.
- **The backend still trusts client-supplied email content.** `verdictHeading`/`verdictBody`/`adviceText`/checklist items are attacker-controllable free text (length-capped, HTML-encoded so no injection) that gets embedded in a NOVIRA-branded email sent from the shared Resend account to *any* address the caller supplies. Rate limiting bounds how many such emails one IP can trigger, but doesn't eliminate the "our infrastructure could be used to send a handful of branded messages to an arbitrary inbox" risk. A full fix means the backend stops trusting client-supplied display text entirely (e.g. only accepting a `userId`/answer-hash and regenerating everything server-side) — a bigger architecture change, not done here.
- The in-memory frontend rate limiter (`src/lib/rate-limit.ts`) is process-local: resets on redeploy and won't be shared across instances if this ever runs on multiple servers or serverless — fine for the current single-process dev/prod setup, not for a scaled (multi-instance) deployment specifically; a different concern from the "Pre-deployment blockers" list above, which applies even to a single-instance deployment.
- `ASPNETCORE_ENVIRONMENT`, CORS origin, Resend domain verification — see "Pre-deployment blockers" above, not repeated here.

### Account signup (magic-link auth, built 2026-08-12)
The free signup boundary from `Plan.md` §4 — "see real matches, still free," not the paid Tier 2 document-verification boundary. Researched against real sources before building (OWASP's Forgot Password Cheat Sheet, ASP.NET Core Identity's own passwordless token-provider patterns) — see the design reasoning inline in `backend/Endpoints/AuthEndpoints.cs`'s doc comment, summarized here.

- **Email-only, no password anywhere** — avoids storing/hashing a whole second class of secret, matches the "medium security, not crazy strict" bar already set for the admin key, reuses the Resend integration already built for result emails.
- **No full ASP.NET Core Identity** — deliberately lightweight/custom instead, consistent with the codebase's minimal style elsewhere (plain EF entities, no DI-heavy machinery until needed). Identity would pull in its own `UserManager`/`SignInManager`/migrations for a `User` model that already has a real custom shape (the Tier 1 profile snapshot fields).
- **Two DB-backed token kinds**, both hashed at rest per OWASP (never store the raw bearer secret) — hashing/generation shared via `backend/Services/TokenGenerator.cs` (256-bit CSPRNG tokens, SHA-256 hashed, Base64Url-encoded so they drop into a URL safely):
  - `MagicLinkToken` (`Models/MagicLinkToken.cs`) — 15-minute expiry, single-use, proves "this browser owns this email." Requesting a new link invalidates any still-unused prior one for that user. Single-use is enforced with an **atomic conditional `ExecuteUpdateAsync`** (`UPDATE ... WHERE TokenHash = @hash AND UsedAt IS NULL`, checking rows-affected), not a read-then-write — closes a real race where two concurrent verify calls for the same token could both read `UsedAt == null` before either write finished, which mattered here because some email clients/gateways pre-fetch links to scan them for phishing before the real user clicks. Verified live by firing two literally-concurrent verify requests at the same token: exactly one won (got a session), the other failed with the same generic error as an already-used token.
  - `Session` (`Models/Session.cs`) — 30-day expiry, created only after a successful verify, proves "logged in." A **real DB row, not a stateless signed cookie** — deliberately diverges from the common ASP.NET Core Identity passwordless pattern, because a stateless token can't be revoked without rotating the key ring for every user at once, and needs production key-ring persistence (disk/Blob/KeyVault) this app doesn't otherwise depend on. A DB row means logout is a real revocation (delete the row), verified live: calling `/auth/me` with a just-logged-out token returns 401. Kept as its own table (not columns on `Users`) specifically so signing in on a second device doesn't silently log out the first.
- **The backend never sets a browser cookie directly.** `POST /auth/verify` returns the raw session token in its JSON body; only the Next.js Route Handler (`frontend/src/app/api/auth/verify/route.ts`) turns that into the actual `HttpOnly`/`Secure`/`SameSite=Lax` cookie (`novira_session`, name/expiry shared via `frontend/src/lib/session-cookie.ts`) — same "browser never talks to the backend directly" rule the rest of the app already follows. The raw token is never echoed back into any client-visible JSON response after that point. Every authenticated proxy route (`/api/auth/me`, `/api/auth/logout`, `/api/matches`) reads the cookie server-side and forwards it to the backend as `X-Session-Token`, validated by `backend/Endpoints/SessionAuthFilter.cs` (the session-auth counterpart to `AdminAuthFilter`).
- **Endpoints**: `POST /auth/request-link`, `POST /auth/verify`, `GET /auth/me`, `POST /auth/logout` (`backend/Endpoints/AuthEndpoints.cs`), plus `GET /matches` (`MatchingEndpoints.cs`, session-authenticated) — the real signup payoff: full `MatchResult` details (names, providers, fit factors), not just counts like the public `/opportunity-counts`. Backend-rate-limited (`auth-request-link`, `auth-verify` policies) — token brute-forcing is already computationally infeasible given 256 bits of entropy, the rate limit is OWASP's recommended defense-in-depth backstop, not the primary defense. `/auth/request-link` also has its own frontend-level limiter (`frontend/src/app/api/auth/request-link/route.ts`), matching `leads`/`opportunity-counts`; **`/auth/verify` does not** — found in the second self-review pass below, left open as low-priority (the entropy argument already covers the real risk).
- **One `Users` table, no separate "auth identity."** Requesting a magic link upserts by normalized email exactly like `/leads` does — a user who already captured their email via `SaveResultPrompt.tsx` just authenticates into that same row; signing up never forks a second identity.
- **Anti-enumeration where it actually matters, honest delivery status where it doesn't.** `/auth/request-link` reports the *real* `emailSent` status (not a hardcoded `true`) — revealing whether the email actually sent doesn't leak whether the account already existed (the account is upserted either way, and Resend succeeding/failing is independent of that), and hiding a genuine send failure would mean a misconfigured/down Resend silently stranding every signup with no visibility to the user or the founder, the same reasoning `/leads`' own `emailSent` field already relies on. Verified live: with `Resend:ApiKey` unset locally, the endpoint correctly reports `{ "emailSent": false }` rather than a false `true`; `SignupPrompt.tsx` shows a distinct "we couldn't send that email" message in that case instead of a false "check your inbox." `/auth/verify` still returns one identical "This link is invalid or has expired" message whether the token was never valid, already used, expired, or lost the single-use race above — verified live that reusing an already-verified token and submitting a garbage token both produce the exact same response.
- **Dev-only convenience, not production behavior**: when `ASPNETCORE_ENVIRONMENT=Development`, `/auth/request-link` also logs the raw magic-link URL (`[DEV ONLY]` prefix) so the flow is testable without a working Resend account in every local session. Gated on `IHostEnvironment.IsDevelopment()`, never touches the response body, and stops working entirely once the app runs in Production (see the `ASPNETCORE_ENVIRONMENT` known-limitation note below, shared with the rest of the app).
- **Frontend**: `SignupPrompt.tsx` (rendered on `/assessment/result` right after `OpportunityCounts.tsx`, replacing what used to be that component's static "sign up to see the actual opportunities" sentence with a real working CTA) — checks `/api/auth/me` on mount and skips straight to a "View my matches" link if already signed in, otherwise shows the email-request form with idle→submitting→"check your email" states (same pattern as `SaveResultPrompt.tsx`). `frontend/src/app/auth/verify/page.tsx` is the link-landing page (wrapped in `<Suspense>` — `useSearchParams()` requires it or the production build fails to prerender the route, hit and fixed during this build). `frontend/src/app/matches/page.tsx` is the authenticated results page, with its own "self-reported, not yet verified" disclaimer per `Plan.md` §4 and a working sign-out.
- **Verified end-to-end live** (not just unit-level): real request→dev-log token→verify→redirect-to-`/matches`→cookie is genuinely `HttpOnly`/`SameSite=Lax`→`SignupPrompt` correctly shows "already signed in" on a revisit→logout→`/matches` correctly shows signed-out→the old token is confirmed dead against the real backend (401), not just forgotten client-side. Test user rows deleted from Neon after verification — re-queried `MagicLinkTokens`/`Sessions` directly afterward and confirmed 0 rows remained, actually confirming the FK cascade (not just assuming it from the config).
- **Self-review pass #1 (2026-08-12), same day as the initial build**: re-read every file with a security-review lens and found/fixed three real issues before this reached any real user — the `emailSent`-always-true anti-pattern and the non-atomic single-use race described above, plus a frontend status-code bug in `frontend/src/app/api/auth/verify/route.ts` (`backendResponse.status || 400` would have returned an error body with a *200* status in an edge case where the backend responds 200 without a usable `sessionToken` — `200` is truthy, so `|| 400` never applied; fixed to check the missing-token case separately and force a real error status). Known, deliberately-not-fixed characteristic shared with `/leads`: the email-upsert's check-then-insert isn't atomic either (a narrow concurrent-signup race could hit the DB's unique-email-index constraint and 500 once, requiring a retry) — pre-existing pattern, not a regression introduced here.
- **Self-review pass #2 (2026-08-12), broadened to the whole app, not just the new auth files**: found the `X-Forwarded-For` rate-limit gap now tracked in "Pre-deployment blockers" above (app-wide, not auth-specific, but most consequential on `/auth/request-link` — see that section for the full reasoning). Also found and left open (lower priority, not yet fixed): `frontend/src/app/api/auth/verify/route.ts` has no frontend-level `isRateLimited` check, unlike every other sensitive proxy route in the app — low actual risk given the token's 256 bits of entropy already make brute-forcing infeasible, but worth closing for consistency/defense-in-depth. Also noted, not fixed, genuinely minor: a faint timing side-channel in `/auth/request-link` (the new-account path does one extra DB round-trip the existing-account path skips, a low-value email-enumeration signal); `/auth/logout` re-resolves the session `SessionAuthFilter` already resolved instead of reusing it (inefficient, not incorrect); `GET /matches` loads the entire `Opportunities` table into memory every call (fine at current scale, will need real SQL-level filtering as the multi-source/multi-country data volume referenced in the "Data architecture strategy" item above actually grows).
- **Real bug found and fixed (2026-08-16): signing up straight from `SignupPrompt.tsx` produced a Users row with an empty profile snapshot.** Root-caused via direct DB query (a freshly-signed-up user had every profile field null) then confirmed in code: `RequestLinkRequest` only ever carried `Email`, never a `ProfileSnapshot` — unlike `/leads`'s `SaveResultRequest`, which does — and `SignupPrompt` (rendered on `/assessment/result` with zero props) had no way to send one even though `result/page.tsx` already computes `profile = buildProfileSnapshot(answers)` and passes it to `SaveResultPrompt`/`OpportunityCounts` right next to it. This made `/opportunity-counts` (which recomputes fresh from the in-browser answers on every call) show a real count while `/matches` (which reads the persisted row) showed nothing, for the same in-progress profile — the exact discrepancy that surfaced this. Fixed symmetrically end to end: `RequestLinkRequest` (both `AuthEndpoints.cs`'s record and `contracts/auth.ts`'s interface) gained an optional `profile`; `/auth/request-link`'s handler now writes it onto the `Users` row with the same overwrite-on-every-capture semantics as `/leads` (field-for-field identical block); `SignupPrompt` now takes a required `profile: ProfileSnapshot` prop, sends it in `requestMagicLink`, and `result/page.tsx` passes the same `profile` object it already hands to the other two components. (`ProfileSnapshot`, a `Program.cs`-local record, had to go from its default `internal` to `public` — `AuthEndpoints.cs`'s already-`public` `RequestLinkRequest` can't expose a less-accessible member type, CS0051.) Verified live end to end, not just compiled: a real `/auth/request-link` call with a full profile → confirmed via `/admin/users/{id}` that every field persisted → verified the dev-logged token → called the real `/matches` with the resulting session and got back real Ausbildung/University rows with fit factors, where before the fix it would have returned nothing. Test user deleted afterward via the real `DELETE /account` endpoint (also incidentally re-confirms that endpoint still works).
- **Security fix (2026-08-28, found in code review): the fix above had introduced a real vulnerability — writing the profile at request time, before proving inbox ownership.** Anyone who knew a victim's email could POST to `/auth/request-link` with a bogus profile and silently corrupt the victim's stored data (feeding real `/matches` results), without ever clicking the link or proving they own that inbox. Fixed by deferring the write: `MagicLinkToken` gained `PendingProfileJson` (the JSON-serialized profile rides along on the token, not the `User` row); `/auth/verify` now applies it to `user` only after the atomic single-use claim succeeds — i.e. only once whoever clicked the link has proven inbox ownership. See "Pre-deployment blockers"/"Known issues from code review" above for the checklist entry and the live attack-scenario verification (confirmed a bogus-profile request left the victim's real data untouched until — and unless — the link was actually consumed).
- **Standalone `/signin` entry point (built 2026-08-28) — closing a real "how do I get back in" gap.** Walking through the auth UX with the founder surfaced this: the *only* place that could request a magic link was `SignupPrompt.tsx`, which only renders on `/assessment/result` — and that page hard-requires a saved assessment in `localStorage`, showing "We couldn't find a saved assessment" with just a link to redo the entire 14-question assessment if none exists. ### Document verification pipeline (built 2026-08-15, verified end-to-end)

Level 2/3 of the four-level user-data model referenced since Phase 1 (self-report → AI document verification → human verification → future AI/human interview — see `Models/User.cs`'s comment and `Plan.md`). Explicitly scoped to the founder's own synthetic/fake documents for now — real user submissions stay gated on the Phase 0 legal review, see "Deferred" above. This is the **first real LLM/AI call anywhere in the live app** — the Tier 1 verdict, eligibility check, and opportunity matching are all deliberately rule-based (zero marginal cost, no latency, no hallucination risk, see "Matching algorithm" above) because a rule sufficed and the stakes were high; document verification is a genuinely different case, because the input is an unstructured scanned image/PDF that no rule can read.

**Pipeline shape**: upload → AI verification (automatic, synchronous, on upload) → human review (admin) → decision (Approve / Deny / Flag red / free-text message).

- **Schema**: `UserDocument` (`Models/UserDocument.cs`) — `DocumentType` (`Passport`/`EducationCertificate`/`LanguageCertificate`/`Other`; only the first two are exposed in the upload UI for now, since those are what's realistic to test with fake documents), `AiVerificationStatus` (`Pending`/`Completed`/`Failed` — did the AI step itself succeed, independent of what it found), `DocumentReviewStatus` (`PendingReview`/`Approved`/`Denied`/`FlaggedRed` — the human's decision). `User.cs` gained `FraudFlagged`/`FraudFlaggedAt`/`FraudFlagNote` (`FullName` already existed as a nullable self-reported field from an earlier build).
- **Storage**: `AzureBlobStorageService` — a private Azure Blob container (`users-documents`, no anonymous access; Firebase Storage was the original suggestion but Azure Blob won out for the native .NET SDK fit and to avoid adding a second cloud ecosystem to an otherwise Azure+.NET+Postgres stack, see the "Database hosting" note above for the same reasoning applied to the DB). Uploads are proxied through the backend, never browser→Azure directly — same "keep the credential server-side" discipline as every other secret in this app. The admin review UI never gets a permanent link either: `GenerateReadSasUri` mints a 15-minute, read-only, single-blob SAS URI on each detail-page fetch.
- **AI extraction**: `DocumentVerificationService` — calls Claude Opus 5 with vision (an `image` content block for JPEG/PNG, a `document` content block with `Base64PdfSource` for PDFs) and `output_config.format` (structured JSON output, not a free-text opinion) to extract a fixed schema: detected document type, extracted full name, issuer/institution, expiry date, legibility, a `nameMatchesProfile` judgment, a list of concrete `concerns`, and a one/two-sentence `summary` for the admin UI. The name-match check is a model judgment (allows for spelling/order/transliteration variance) against the user's self-reported `FullName` passed in the prompt — never an exact string comparison, and a mismatch becomes a flag for the human to see, **never** an automatic overwrite of `FullName`. Runs synchronously inside `POST /documents` so a document already has AI findings by the time any human opens it — no separate "run AI" trigger exists.
- **Considered and rejected**: turnkey identity-verification platforms (Onfido, Persona, Veriff, Stripe Identity, Sumsub) do genuinely combine hosting + AI verdict + fraud/liveness checks as one product, but are enterprise/compliance-oriented, cost per verification, and would replace the actual thing being tested (whether a Claude-based pipeline works for this) with someone else's black-box verdict. Worth revisiting only at real production volume with real compliance needs, not now.
- **Human review** (`DocumentsAdminEndpoints.cs`, admin-key protected, same `AdminAuthFilter` as `/admin/opportunities`): `GET /admin/users` (search by name/email via `EF.Functions.ILike`, users with any document still `PendingReview` sorted first), `GET /admin/users/{id}` (full self-reported profile + every document with its AI findings + a fresh preview URL), `PATCH /admin/users/{userId}/documents/{documentId}` (the decision — see below), `POST /admin/users/{userId}/message` (free-text email, the escape hatch beyond the three fixed decisions).
- **Approve/Deny/FlagRed is deliberately per-document, not a per-user batch action** — a passport can be approved while a certificate is denied; there is no "approve everything pending for this user" button. `FlagRed` is the one exception with a user-level *consequence*: it's still a per-document button, but setting it also sets `User.FraudFlagged`/`FraudFlaggedAt`/`FraudFlagNote` and blocks further self-service uploads (checked in `POST /documents`) until an admin manually clears it — deliberately no self-service unflag path. `Denied` is distinct from `FlagRed`: a legitimate document that doesn't meet requirements, inviting a reupload, versus a suspected-fraud signal about the person.
- **Email**: `ResendEmailService` — a small, generic Resend sender, deliberately separate from `Program.cs`'s existing inline `SendResultEmailAsync`/`BuildResultEmailHtml` (not refactored into one shared thing, to avoid touching already-verified code for this). Originally sent the full Deny/FlagRed decision content by email; as of the in-app messaging entry below (2026-08-27), it only sends a content-free notification ping — the decision content itself is a `Message` row now.
- **Endpoints**: `GET/POST /documents` (`DocumentsEndpoints.cs`, session-authenticated via `SessionAuthFilter` — any signed-up user, not just the founder), rate-limited (`documents-upload` backend policy, 10/min per IP) since each upload triggers a real, paid Claude API call. Max 10MB, JPEG/PNG/PDF only.
- **Frontend**: `frontend/src/app/account/page.tsx` — the consolidated self-service page (replaced the earlier standalone `/documents` route, 2026-08-16, once the founder flagged the app's navigation as confusing to work with): `ProfileSection` (self-reported, read-only), `VerifiedSection` (Level 3, see below), `DocumentsSection` (one-at-a-time upload — a required name field, no type dropdown since the AI determines type, not the uploader — plus a status list), `MessagesSection` (real in-app messages, see the in-app-messaging entry below — no longer a placeholder), and `DangerZone` (two-step "delete my account" confirm, backed by the real `DELETE /account` below). `frontend/src/app/admin/users/profiles/page.tsx` (list + search + the pending-review section pinned to the top) → `frontend/src/app/admin/users/profiles/[id]/page.tsx` (full profile, `VerifiedSection` counterpart, each document's image/PDF preview + AI findings + the four review actions, the free-text message form, and a `DeleteUserSection` for admin-initiated account deletion). Admin-key gating is now centralized in `frontend/src/app/admin/layout.tsx` — see the admin navigation reorg entry below. `SiteNav` (`frontend/src/components/site-nav.tsx`) is auth-aware — checks `/api/auth/me` on mount and swaps its links/CTA between signed-out ("Start questionnaire") and signed-in ("My matches"/"My account") states, which is what actually makes `/account` and `/matches` discoverable now (previously `/documents` had no nav entry point at all).
- **Self-service account endpoints** (`backend/Endpoints/AccountEndpoints.cs`, 2026-08-16) — the counterpart to the admin-only `DocumentsAdminEndpoints.cs`, session-authenticated like `/documents`/`/matches`: `GET /account` (a signed-in user's own profile, now including the `Verified*` fields below) and `DELETE /account` (full real deletion, not a soft-delete flag — reuses the already-tested FK cascade from the auth-system build and best-effort blob cleanup via `AzureBlobStorageService.DeleteAllForUserAsync`, which never blocks the DB deletion on a storage error). `DocumentsAdminEndpoints.cs` also gained `DELETE /admin/users/{id}` (same real deletion, admin-key protected) for cases the user themself can't or won't act on, e.g. a fraud-flagged account — verified live: unauthenticated delete correctly 401s, authenticated delete 204s and the user is genuinely gone afterward (list empty, detail 404).
- **Verified end-to-end live (2026-08-15)**, real Anthropic API key, real uploads through the actual `/documents` UI. The AI genuinely did real verification work, not a rubber stamp: on a document uploaded as "Passport," it correctly identified it was actually an Egyptian travel-movement certificate (not a passport at all) and flagged the type mismatch, redacted fields, and missing page; on a real passport photo, it correctly extracted the full name/DOB/issue/expiry dates *and* flagged that the passport was expired, that the MRZ strip was cropped out of frame, and — notably — that a watermark pattern suggested the image might be sourced from the internet rather than a personal scan (a real fraud-adjacent signal, unprompted). Both rows landed with `AiVerificationStatus = Completed` and no exceptions.
- **Real bug found and fixed during this pass**: `Azure:Storage:ConnectionString` had been silently truncated to just `DefaultEndpointsProtocol=https` — the rest was lost because the full connection string (which contains `;`) was originally pasted into a PowerShell prompt running `dotnet user-secrets set`, and PowerShell treats unquoted/improperly-quoted `;` as a statement separator. Surfaced as `System.FormatException: No valid combination of account information found` from `AzureBlobStorageService`'s constructor on the very first real upload attempt. Fixed by re-setting the secret from a shell that preserves the literal string. **Lesson for any future connection-string-shaped secret**: verify with `dotnet user-secrets list` immediately after setting it, don't assume the set succeeded just because the command exited 0.
- Both items originally tracked here as "planned next" — a self-service account page, and in-app messaging replacing email for post-signup updates — are now built; see the self-service account endpoints entry above and the in-app messaging entry below. Full self-service *editing* of profile answers is still deliberately out of scope (re-validation plus its interaction with already-verified documents makes it a bigger piece) — redoing the assessment remains the rough-edge stand-in for now.
- **Frontend has other real problems flagged by the founder, not yet itemized** — noted here so it isn't lost, but nothing specific enough yet to act on; needs a follow-up pass once the founder lists what's actually wrong.

### Verified profile data (Level 3, built 2026-08-16)

Until now the document pipeline's AI extraction was a dead end: it informed the human reviewer but never flowed anywhere else. The founder wanted document data (once verified) to actually improve match quality and start building the richer profile a future "apply on the user's behalf" feature would need. `User.cs` gained 11 `Verified*` fields (`VerifiedFullName`/`VerifiedDateOfBirth`/`VerifiedNationality`/`VerifiedPassportNumber`/`VerifiedPassportExpiryDate`/`VerifiedPassportStatus`/`VerifiedHighestEducation`/`VerifiedFieldOfStudy`/`VerifiedGermanLevel`/`VerifiedEnglishLevel`/`VerifiedDataUpdatedAt`) — a distinct layer from the existing Level‑1 self-reported fields, not a replacement for them.

- **Trust boundary**: promotion happens only when an admin clicks **Approve** on a document (`DocumentsAdminEndpoints.cs`'s new `ApplyVerifiedDataFromDocument`), never the moment AI extraction completes. This deliberately extends, rather than breaks, the pipeline's existing rule that AI judgment alone must never silently overwrite identity fields (`AiNameMatchesProfile` was already documented as "never used to silently overwrite `User.FullName`") — an explicit human Approve action isn't silent. No unwind logic is needed for Deny/FlagRed since nothing is ever written to the account until Approve. Documents approved *before* this existed are not retroactively backfilled.
- **Extraction** (`DocumentVerificationService.cs`) gained 7 new schema-constrained fields, empty-string sentinel when not applicable to the document at hand (same convention as the pre-existing `expiryDate`/`issuerOrInstitution`): `dateOfBirth`/`nationality`/`documentNumber` (Passport), `highestEducationLevel` (enum-constrained to `EducationLevel`'s members, so it parses straight into the enum) /`fieldOfStudy` (EducationCertificate), `certifiedLanguage` (`German`/`English`) + `certifiedLevel` (enum-constrained to the full interleaved `LanguageLevel` member set, with the prompt explicitly requiring the CEFR subset for German and the casual subset for English — same cross-scale reasoning as the enum's own comment in `Opportunity.cs`).
- **Matching** (`MatchingService.cs`) now reads `profile.VerifiedHighestEducation ?? profile.HighestEducation` (hard filter) and `profile.VerifiedGermanLevel ?? profile.GermanLevel` / `VerifiedEnglishLevel ?? EnglishLevel` (soft factors) — a verified value, when present, wins over the self-report. When a factor actually used a verified value, its label gets a `" — verified"` suffix so the match list itself communicates why. `VerifiedPassportStatus`/identity fields aren't consumed by scoring yet (no existing hook for them) — captured for the account/future-application use case, not wired into matching.
- **Frontend**: `Account`/`AdminUserDetail` both gained a shared `VerifiedProfile` contract (`frontend/src/lib/contracts/leads.ts`); `/account` and `/admin/users/profiles/[id]` each render a `VerifiedSection` (emerald "Verified from your documents"/"Confirmed" styling, only rendered when at least one field is set) distinct from the existing self-reported section, which correctly keeps saying "not yet independently verified" since it's scoped to Level‑1 fields only. The admin `DocumentCard` also surfaces the 7 new AI-extracted fields pre-approval, with a note that approving writes them onto the account. `/matches`' page-level disclaimer copy updated from "self-reported answers — not yet verified" to "self-reported answers, plus anything confirmed from your approved documents."

### Backend conventions
- Minimal API, not MVC controllers — but no longer single-file. `Program.cs` is the composition root (DI registration, middleware, the inline `POST /leads` handler + its helpers) and delegates route groups to `Endpoints/*.cs` extension methods (`MapOpportunitiesAdminEndpoints()`, `MapMatchingEndpoints()`, `MapAuthEndpoints()`, `MapDocumentsEndpoints()`, `MapDocumentsAdminEndpoints()`, `MapAccountEndpoints()`, `MapMessagesEndpoints()`), each called once from `Program.cs`. `Models/` holds `User.cs`, `Opportunity.cs`, `MagicLinkToken.cs`, `Session.cs`, `UserDocument.cs`, `Message.cs` (each file also declares its own small backend-mirror enums, e.g. `LanguageLevel`, `EducationLevel` in `Opportunity.cs`, reused by `User.cs` — see the "Matching fields" bullet above for why these mirror the frontend's enums instead of being shared code). `Services/MatchingService.cs` and `Services/TokenGenerator.cs` are static-method business logic with no DI/interfaces; `AzureBlobStorageService.cs`, `DocumentVerificationService.cs`, and `ResendEmailService.cs` (added for the document pipeline, see below) are the first services registered through DI instead, since each wraps a real external client (`BlobContainerClient`, `AnthropicClient`, `IHttpClientFactory`) that a plain static method can't hold.
- `backend/Data/AppDbContext.cs` is the EF Core context (`Users`, `Opportunities`, `MagicLinkTokens`, `Sessions`, `UserDocuments` DbSets — all but `Opportunities` have a Fluent-API-configured FK to `Users` with no navigation property, same minimal style as everything else). Connection string lives in **.NET user-secrets** (`ConnectionStrings:DefaultConnection`), not in `appsettings.json` — never commit it. Npgsql needs the `Host=...;Port=...;Database=...;Username=...;Password=...;SSL Mode=Require` keyword format.
- **Database hosting — migrated Neon → Azure Database for PostgreSQL Flexible Server (2026-08-15).** Moved deliberately early, while the dataset was still small (2 Users, 83 Opportunities at the time), specifically because a same-engine Postgres→Postgres move only gets riskier once real users and real documents are in it — see the git history/conversation around this date for the full reasoning (mainly: consolidating onto one cloud vendor now that Azure Blob Storage is also part of the stack, and unlocking Managed-Identity auth to the DB later, pre-production). Migrated via a throwaway Npgsql console script (schema-identical copy, `Users` before its FK-dependents) rather than `pg_dump`/`pg_restore`, because the local `pg_dump` (17.5) refused to dump from Neon's server (18.4) — a newer-than-tool-version mismatch. **Known gotcha hit during the move**: Neon's connection role has an empty `search_path` (`current_schema()` returns blank), so unqualified table references resolve fine in EF-generated DDL but fail for a plain `SELECT * FROM "Users"` — always schema-qualify (`public."Users"`) when scripting directly against Neon. Server: `novira-postgres`, Burstable B1ms, West US region — **not EU**, see "Pre-deployment blockers" below.
- Also in user-secrets: `Resend:ApiKey`, `Resend:FromAddress` (email sending, see "Email capture & result email" above). `Frontend:BaseUrl` is a plain (non-secret) config value read from `IConfiguration`, defaulting to `http://localhost:3000` if unset — update it alongside the CORS origin below when a production frontend domain exists.
- EF Core packages are pinned to the 9.x line (`Npgsql.EntityFrameworkCore.PostgreSQL` 9.0.4, `Microsoft.EntityFrameworkCore.Design` 9.0.9) — the package's latest major targets net10.0 and is incompatible with this net9.0 project; don't let a bare `dotnet add package` float it forward.
- CORS is locked to `http://localhost:3000` (the frontend dev origin) — see "Pre-deployment blockers" above.
